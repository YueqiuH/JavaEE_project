# 智慧校园项目数据库变更规范

## 1. 目的与适用范围

本规范用于约束智慧校园项目中的数据库结构、基础数据和迁移历史变更，确保所有小组成员从 GitHub 拉取代码后，可以使用同一套 Flyway 迁移正常初始化或升级本地数据库。

本规范适用于所有涉及表、字段、索引、约束、权限数据、菜单数据、初始化数据和数据修复的改动。

## 2. 基本原则

1. 数据库结构只能通过 Flyway 迁移文件修改，禁止只在本地使用 Navicat、IDEA Database 或 MySQL 客户端手工改表。
2. 已经提交到共享分支，且可能被任何成员执行过的迁移文件永久不可修改、删除或重命名。
3. 每次数据库调整都必须新增迁移文件，通过向前迁移完成。
4. 数据库变更、Java Entity、Mapper、Service、接口和前端调用应在同一个 PR 中保持一致。
5. 小组成员拉取代码后，不需要手动执行零散 SQL；启动项目时由 Flyway 自动升级数据库。
6. 迁移必须同时兼容已有开发数据库升级和全新数据库初始化。

## 3. 迁移文件位置

自动执行的 SQL 迁移统一放在：

```text
backend/campus-app/src/main/resources/db/migration/
```

默认使用 SQL 迁移。只有必须读取旧库状态或进行复杂条件判断时，才允许新增 Java Migration：

```text
backend/campus-app/src/main/java/db/migration/
```

项目根目录下的 `database/migration/` 不会被当前 Spring Boot 自动执行，只能作为历史资料或辅助脚本，不能作为正式迁移入口。

## 4. 迁移文件命名

现有 `V1` 到 `V6` 全部冻结。从现在开始建议使用时间戳版本，避免多人同时创建相同版本：

```text
VyyyyMMddHHmmss__英文描述.sql
```

示例：

```text
V20260720103000__add_course_audit_columns.sql
V20260720110000__remove_graduation_design.sql
V20260720113000__create_asset_inventory_index.sql
```

命名要求：

- 时间使用北京时间，精确到秒。
- 版本号与描述之间必须使用双下划线 `__`。
- 描述使用小写英文和下划线。
- 文件创建前在小组内声明版本号，防止重复。
- 有依赖关系的迁移必须按执行顺序分配时间。
- 文件一旦进入共享分支，不得改名。

## 5. 严禁操作

禁止修改已经执行过的 `V1`、`V2` 等历史迁移。即使只修改注释、空格或换行，也可能改变 Flyway checksum。

严禁以下操作：

- 执行 `flyway repair` 掩盖 checksum 冲突。
- 手工修改 `flyway_schema_history`。
- 删除或重命名历史迁移。
- 在 `application.yml` 中关闭 Flyway 校验。
- 将个人数据库密码提交到 Git。
- 在正式迁移中加入个人测试数据。
- 未备份就执行 `DROP TABLE`、`DROP COLUMN` 或批量 `DELETE`。
- 使用没有 `WHERE` 条件的 `UPDATE` 或 `DELETE`。
- 为了让本机通过而加入只适用于个人数据库状态的 SQL。

## 6. 常见数据库修改方式

### 6.1 新增表

```sql
CREATE TABLE `course_audit` (
    `audit_id` BIGINT NOT NULL AUTO_INCREMENT,
    `course_id` BIGINT NOT NULL,
    `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`audit_id`),
    KEY `idx_course_audit_course_id` (`course_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

新表必须明确主键、必要索引、字符集和字段是否允许为空。

### 6.2 新增字段

新增字段时，优先允许为空或提供合理默认值，避免已有数据迁移失败：

```sql
ALTER TABLE `course`
    ADD COLUMN `audit_status` TINYINT NULL COMMENT '审核状态';
```

如果字段最终要求 `NOT NULL`，建议分阶段处理：先新增可空字段、回填历史数据，再通过后续迁移增加非空约束。

### 6.3 删除功能或表

删除功能时，不允许从旧迁移中删除原建表语句，应新增迁移：

```sql
DROP TABLE IF EXISTS `graduation_report`;
DROP TABLE IF EXISTS `graduation_selection`;
DROP TABLE IF EXISTS `graduation_topic`;
```

存在外键关系时，必须先删除子表或外键，再删除父表。禁止通过全局关闭外键检查掩盖依赖问题。

### 6.4 修改字段类型或名称

修改前必须确认已有数据可以转换。高风险修改应采用以下步骤：

1. 新增目标字段。
2. 迁移并校验旧字段数据。
3. 修改代码读取新字段。
4. 在后续迁移中删除旧字段。

不要直接修改包含重要数据的字段类型或名称。

### 6.5 新增索引和唯一约束

新增唯一约束前，必须先检查并处理重复数据。索引名称应表达表和字段，例如：

```sql
ALTER TABLE `course`
    ADD UNIQUE KEY `uk_course_code` (`course_code`),
    ADD KEY `idx_course_status` (`status`);
```

## 7. 数据和种子数据规范

1. 表结构迁移与演示数据尽量拆分成不同迁移文件。
2. 种子数据必须使用稳定业务键，例如账号、编码或唯一索引，不能依赖固定自增 ID。
3. 必要的初始化数据应使用明确的重复处理策略，例如 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE`。
4. 测试数据、压力测试数据和个人调试数据不得放入正式迁移。
5. 演示数据确需提交时，必须在文件名和注释中说明用途。
6. 大批量数据修复必须先备份，并在 PR 中说明影响行数和恢复方案。

## 8. 成员修改流程

1. 拉取最新共享分支，确认本地迁移版本是最新的。
2. 创建自己的功能分支。
3. 在小组内登记准备使用的迁移时间戳和变更内容。
4. 新增迁移文件，不修改任何历史迁移。
5. 同步修改 Entity、Mapper、Service、接口、测试和前端调用。
6. 使用已有数据库验证增量升级。
7. 使用全新临时数据库验证完整初始化。
8. 运行后端测试和构建。
9. 提交 PR，并写清楚数据库影响和验证结果。
10. 合并前再次同步目标分支，检查迁移版本和数据库对象是否冲突。

## 9. 必须完成的两类验证

### 9.1 现有数据库升级验证

- 保留已经执行过的 Flyway 历史。
- 拉取新代码后启动应用。
- 确认新迁移成功执行。
- 确认原有数据没有丢失。
- 确认主要接口正常。
- 确认 `flyway_schema_history` 中新增迁移的 `success` 为 `1`。

### 9.2 空数据库初始化验证

- 使用单独的临时数据库，不得覆盖日常开发数据库。
- 从最早迁移执行到最新迁移。
- 确认全部迁移成功。
- 确认最终表结构与升级后的现有数据库一致。
- 确认演示账号和必要基础数据可用。

建议执行：

```powershell
mvn test
mvn install -DskipTests
mvn -pl backend/campus-app spring-boot:run
```

## 10. PR 数据库检查清单

PR 描述必须包含：

- 新增的迁移文件名称。
- 修改了哪些表、字段、索引、约束或数据。
- 是否涉及删除或其他不可逆操作。
- 是否需要提前备份。
- 对 Java Entity、Mapper、接口和前端的影响。
- 现有数据库升级结果。
- 空数据库初始化结果。
- Flyway 最终执行记录。

审查人员必须确认历史迁移没有被修改：

```powershell
git diff origin/main...HEAD -- backend/campus-app/src/main/resources/db/migration
```

正常情况下，输出只能包含新增迁移文件。不能出现历史迁移的修改 `M`、删除 `D` 或重命名。

## 11. 拉取代码后的标准运行方式

成员拉取最新代码后，应先设置本机数据库连接环境变量，再启动后端。不要修改并提交公共配置中的个人密码。

```powershell
$env:DB_URL = "jdbc:mysql://localhost:3306/school_spring?serverTimezone=Asia/Shanghai&useUnicode=true&characterEncoding=utf-8&allowMultiQueries=true&createDatabaseIfNotExist=true"
$env:DB_USERNAME = "root"
$env:DB_PASSWORD = "个人本地数据库密码"
mvn -pl backend/campus-app spring-boot:run
```

Flyway 会自动执行尚未运行的迁移。成员不应重复导入 `init.sql`，也不应逐个手工执行迁移文件。

## 12. checksum 错误处理

发现以下错误后必须立即停止：

```text
Migration checksum mismatch
```

处理步骤：

1. 找出哪个历史迁移被修改。
2. 从修改前的 Git 提交精确恢复该文件。
3. 将真正需要的数据库变更写入新的迁移。
4. 分别验证旧数据库升级和空数据库初始化。
5. 通过 PR 合并修复。

不得通过 `flyway repair`、修改历史表或关闭校验绕过问题。

## 13. 备份与不可逆变更

执行删除表、删除字段、批量清理或不可逆数据转换前，必须：

1. 导出受影响表或完整数据库备份。
2. 在 PR 中说明不可逆影响。
3. 提供回退或数据恢复方案。
4. 获得模块负责人和数据库变更审查人的确认。

Flyway Community 默认不提供自动 Undo。迁移上线后发现问题，应新增修复迁移，不得修改已经执行的文件。

## 14. 核心规则

> 已执行的迁移是项目历史，只能新增，不能改写。
