# 智慧校园服务平台架构基线

> 版本：v1.0<br>
> 冻结日期：2026-07-16<br>
> 状态：团队确认<br>
> 适用分支：`develop` 及其功能分支

本文档是项目架构、接口和协作边界的最高优先级基线。其他指南、示例代码与本文冲突时，以本文为准。公共规范需要变更时，必须先在 PR 中更新本文，再修改实现。

## 1. 实施范围

四名成员各负责 5 个必做功能，成员 A、D 另有 AI 加分项：

| 成员 | 必做 | 加分项 |
| --- | --- | --- |
| A | A1-A5 | A6 AI 智能学习助理 |
| B | B1-B5 | 无 |
| C | C1-C5 | 无 |
| D | D1-D5 | D6 AI 自然语言报表助手 |

AI 功能不得阻塞必做功能的构建、启动、测试或验收。未配置模型密钥时，核心项目必须能够正常运行。

## 2. 总体架构

项目采用前后端分离的模块化单体。后端只部署一个 Spring Boot 应用，四名成员在 `campus-app` 内按业务包隔离开发；前端只部署一个 Vue 应用，四名成员按视图目录隔离开发。

### 2.1 Maven 模块

```text
campus-parent
├─ backend/campus-common
├─ backend/campus-contract
├─ backend/campus-auth
└─ backend/campus-app
```

- `campus-common`：统一响应、异常、分页、日志和公共配置。
- `campus-contract`：Entity、DTO、VO、权限码和稳定公共契约。
- `campus-auth`：登录、Token、当前用户和权限校验。
- `campus-app`：唯一启动模块，同时承载按业务域分包的 Controller、Service 和 DAO。

### 2.2 后端业务包

```text
com.smartcampus.app
├─ controller/{teaching,student,office,base}
├─ service/{teaching,student,office,base}
└─ dao/{teaching,student,office,base}
```

成员只能在自己负责的业务包内新增业务代码。不同业务包之间禁止直接调用 Service；跨域协作使用冻结的 ID、只读查询或 `campus-contract` 中的稳定契约。

### 2.3 前端业务目录

```text
frontend/src/platform/src
├─ views/teaching
├─ views/student
├─ views/office
├─ views/base
└─ api
```

成员分别维护自己的 `views/<domain>`。第二阶段将公共 `api/getData.js` 拆分为 `api/teaching.js`、`api/student.js`、`api/office.js` 和 `api/base.js`，避免多人同时修改同一文件。

## 3. 目录所有权

| 范围 | 负责人 | 规则 |
| --- | --- | --- |
| `controller/service/dao/teaching`、`views/teaching` | A | 只实现 A1-A6 |
| `controller/service/dao/student`、`views/student` | B | 只实现 B1-B5 |
| `controller/service/dao/office`、`views/office` | C | 只实现 C1-C6 |
| `controller/service/dao/base`、`views/base` | D | 只实现 D1-D6 |
| `campus-common`、`campus-auth`、应用级配置、公共前端工具 | 框架负责人（B 兼任） | 其他成员通过 PR 申请修改 |
| `campus-contract`、`database/baseline` | 按数据所有权管理 | 公共结构变更必须在 PR 中说明影响 |

成员可以读取公共文件，但不得为自己的单一功能随意修改公共响应、认证、共享实体或基础表结构。

## 4. 数据所有权

### 4.1 共享数据

- 公共框架维护账号、密码、角色、权限、菜单等认证结构。
- 成员 D 维护学生和教职工基础档案的业务数据与 CRUD。
- 成员 B 只读取学生基础档案，写入学籍异动、奖助贷、评教、竞赛和实验室预约相关数据。
- 成员 A、C 通过冻结的用户或学生 ID 读取所需基础信息，不直接修改基础档案结构。
- `user`、`student`、`menu` 等共享表的字段或约束只能由框架负责人修改。

### 4.2 业务数据

| 成员 | 主要数据范围 |
| --- | --- |
| A | `course`、`score`、`schedule`、`course_selection`、`exam`、`graduation_*`、`classroom` |
| B | `student_status_change`、`scholarship`、`evaluation`、`competition_*`、`lab`、`lab_booking` |
| C | `fee`、`payment`、`asset`、`work_plan`、`document*`、`meeting*`、`notification` |
| D | 基础档案业务、`department`、`major`、`enrollment`、`news`、`forum_*` |

共享 Entity 集中放在 `campus-contract`，但集中存放不代表所有成员都可以修改。需要新增公共字段时，先提交说明变更原因、影响模块和迁移方式的 PR。

## 5. HTTP 接口规范

### 5.1 路径

所有业务接口使用 `/api/v1` 前缀：

```text
/api/v1/auth/**
/api/v1/teaching/**
/api/v1/student/**
/api/v1/office/**
/api/v1/base/**
```

资源路径使用名词和复数形式，操作由 HTTP 方法表达。新增接口不得使用 `/add`、`/update`、`/delete` 等动词路径。

```http
GET    /api/v1/student/scholarships
POST   /api/v1/student/scholarships
GET    /api/v1/student/scholarships/{id}
PUT    /api/v1/student/scholarships/{id}
DELETE /api/v1/student/scholarships/{id}
```

### 5.2 认证

除登录和明确公开的接口外，请求统一携带：

```http
Authorization: Bearer <token>
```

禁止继续新增自定义 `Token` 请求头。未登录返回 HTTP 401，无权限返回 HTTP 403。

### 5.3 统一响应

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "requestId": "01J..."
}
```

错误响应：

```json
{
  "code": 400001,
  "message": "请求参数不合法",
  "data": null,
  "requestId": "01J..."
}
```

- `code = 0` 表示成功，非零值为稳定业务错误码。
- `message` 面向调用方，不返回堆栈或数据库异常详情。
- `requestId` 必须进入响应和服务端日志。
- HTTP 状态码表达协议结果，业务错误码表达具体原因。

### 5.4 分页

分页请求统一使用 `page` 和 `size`，从 1 开始。分页结果放在 `data` 中：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "records": [],
    "total": 0,
    "page": 1,
    "size": 20
  },
  "requestId": "01J..."
}
```

### 5.5 数据格式

- 日期使用 `yyyy-MM-dd`，日期时间使用带时区的 ISO 8601。
- 金额和成绩使用十进制类型，禁止使用浮点数承担精确计算。
- Java `Long` ID 对前端序列化为字符串，避免 JavaScript 精度丢失。
- 空集合返回 `[]`，没有对象时返回 `null`。
- 枚举值、空值规则和字段长度必须在 OpenAPI 中说明。

### 5.6 OpenAPI

每个接口必须包含 `@Tag`、`@Operation`、请求模型、响应模型、权限要求和至少一个错误示例。接口字段变更必须先更新契约，再同步前后端实现。

## 6. Git 协作规则

- `main` 是稳定分支，只接收从 `develop` 发起的发布 PR。
- `develop` 是日常集成分支，功能分支从最新 `develop` 创建。
- 功能分支格式：`feature/<domain>/<description>`。
- 修复分支格式：`fix/<domain>/<description>`。
- 所有变更通过 PR 合并；不要求其他成员批准，作者可以自行合并。
- 合并前必须解决 PR 中已有讨论，并确认检查通过。
- 禁止直接推送、强推或删除 `main` 和 `develop`。
- 每个 PR 只包含一个清晰范围，不混入其他成员的文件。

提交格式：

```text
feat(student): add scholarship application
fix(teaching): validate course capacity
docs(framework): freeze API conventions
```
